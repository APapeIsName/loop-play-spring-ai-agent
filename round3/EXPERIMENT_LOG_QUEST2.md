## 핵심 발견 7가지

### 발견 1 — `MAX_MESSAGES`의 정확한 동작 (바이트코드 검증)

`MessageWindowChatMemory` 생성자 (Spring AI 1.0):
```
Assert.isTrue(maxMessages > 0, "maxMessages must be greater than 0")
```
- **0 이하**: `IllegalArgumentException` → 애플리케이션 시작 실패
- **양수**: 정상

`process()` 로직:
- **SystemMessage 무조건 유지** (자르기 대상 제외)
- USER/ASSISTANT 중 *오래된 것부터* `(size - maxMessages)` 개 잘라냄
- ToolMessage는 **애초에 Memory에 add 안 됨** (Advisor가 `response.getResults()`만 add)

### 발견 2 — Memory 작동률, 윈도우 크기에 *단조 증가*

| MAX | Tool 호출률 |
|---|---:|
| 2 | **16%** |
| 20 | **20%** |
| MAX | **22%** |

→ +4%p, +2%p. 신호 풍부 ↑ → LLM 행동 결정성 ↑. 1단계 발견 1과 같은 라인.

### 발견 3 — 🚨 옛 정보 회수 (turn 8) — MAX_MESSAGES의 진짜 영향

**turn 8 = "아까 1234는 언제 도착해요?"** (5턴 전 정보 회수)

| MAX | 응답에 1234 등장 |
|---|---:|
| 2 | **4/10** (40%) |
| 20 | **10/10 (100%)** ✓ |
| MAX | **10/10 (100%)** ✓ |

**turn 9 = "그 주문 라이더 위치 다시 확인"** (직전 1234 가리킴)

| MAX | 응답에 1234 등장 |
|---|---:|
| 2 | 3/10 (30%) |
| 20 | 9/10 (90%) |
| MAX | 9/10 (90%) |

→ **`MAX_MESSAGES=2`가 옛 정보 회수에서 60% 실패**. 윈도우 1라운드 = 직전 USER/ASSISTANT 한 쌍만 → *"아까"*의 시간 단어가 의미 없음 (회수할 메모리 자체가 없음).

### 발견 4 — turn 7 ("그거 취소") = 가장 어려운 케이스

직전이 *"그럼 1235는 취소되죠?"* → 기대 *"그거" = 1235*

| MAX | 1234 등장 | 1235 등장 |
|---|---:|---:|
| 2 | 4/10 | 1/10 |
| 20 | 5/10 | 4/10 |
| MAX | 6/10 | 4/10 |

**MAX=20에서도 1235 정확도 = 40%**. BaedalPrompt의 *"가장 마지막에 언급된 주문번호 우선"* 가이드가 **부분만 작동**.

→ **단순 *"직전 언급" rule이 LLM에 안 먹힘***. 시퀀스 전체에서 1234가 *초반부터 계속 등장*해 *맥락 무게*가 1234로 쏠림. Round 2 발견 *"가장 마지막"보다 "가장 맥락상 맞는 것"을 LLM이 선택*과 일치.

### 발견 5 — 🎯 turn 10 (요약) — Memory의 진가가 드러나는 자리

**max2 turn 10 응답**:
> r1: *"이전에 다음과 같은 내용을 확인했습니다: 1. 그 주문의 배달 위치를 다시 확인하였습니다."*

→ **마지막 1라운드만 기억**. 시퀀스 *전체 흐름 못 요약*.

**max20 turn 10 응답**:
> r1: *"1. 2024-1235 메뉴 확인. 2. 2024-1234 배달 상태 확인. 3. 1234 취소 시도. 4. 1235 취소. 5. 1234 라이더 위치 재확인."*

→ **전체 시퀀스 정확 요약** ✓

**maxMAX turn 10 응답**:
> r1: *"1. 2024-1234 배달 상황 확인. 2. ETA 4:28. 3. 1235 메뉴 확인. 4. **와퍼 세트 2개 19,000원**. 5. 1235 취소..."*

→ max20보다 *세부 정보 추가 기억* (메뉴, 가격). 단 10턴 시퀀스에선 의미 있는 차이 X.

## 1단계 발견 5 (+1200 토큰 미스터리) 부분 해결

1단계 측정: T2 입력 토큰이 T1보다 +1200 일관 증가. SessionController의 USER/ASSISTANT 4개로는 설명 불가했음.

**2단계 해답**:
- **baseline ≈ 1100** (System Prompt + Tool 스키마 3개)
- **ToolMessage layer ≈ 1500** (MAX 무관하게 누적, 모든 MAX 값에서 동일)
- **USER/ASSISTANT layer**: MAX=2 (≈100) vs MAX=20 (≈1000)
- → 차이 ≈ 1100 ≈ 1단계의 +1200 패턴과 일치

**결론**: T2 +1200 토큰 = **ToolMessage 누적 (Memory 외부 경로) + 1턴의 USER/ASSISTANT (Memory 경로)**. 발견 1 (바이트코드 검증) + 발제 4.5와 정합.

### Part B.3 — 핵심 발견 (Part A 7개 + 신규 5개)

#### 🚨 발견 8 — **MAX=20이 30턴 시점 토큰 *최저***

10턴 측정에선 *정직한 trade-off* (max2 < max20 < maxMAX). 30턴 누적에서는 **역전**:

```
10턴: 2679 (max2) < 3763 (max20) < 3851 (maxMAX) — 정직한 단조 증가
30턴: 4262 (max2) > 3704 (max20) < 4055 (maxMAX) — *V자 패턴*
                          ↑ sweet spot
```

**원인**: max2 → Memory 부족 → Tool 의존 ↑ → ToolMessage layer 누적 ↑ → 결과적으로 *더 많은 토큰*.

→ **MAX_MESSAGES = 20의 두 번째 정량 정당화**: 1단계 옛 정보 회수 100% + 2단계 b 30턴 토큰 *최저* (양 옆 모두 추월).

#### 🚨 발견 9 — Tool 호출률 *반비례*: Memory 적을수록 LLM이 Tool 의존

```
max2:    22.3% (Memory 부족 → 정보 회수 못 함 → Tool 호출로 채움)
max20:    8%   (Memory 충분 → 정보 회수 → Tool 회피)
maxMAX:  22%   (Memory 너무 풍부? 또는 다른 노이즈 — 더 측정 필요)
```

**의미**: *MAX_MESSAGES가 토큰 절약 변수* 만이 아니라 *Tool 호출 의존도 변수*. **두 layer 사이 trade-off**.

#### 🚨 발견 11 — turn 8 옛 정보 회수, 30턴에선 max2 70%까지 회복

**의미**: *시퀀스 자체의 정보 분포*가 MAX_MESSAGES의 효과를 *부분 보완*. *옛 정보가 일찍 한 번* 등장하고 *그 후 안 나오면* max2 망가짐 / *주기적으로 등장*하면 max2도 회복.
